# Why CI on main keeps going red (run 38944460093)

Run 38944460093 is `ci` on main at 5a161f0. All three jobs failed. Every `ci` run on main from 2026-10-12 to 2026-10-16
failed, so this is not one bad commit. Evidence came from the hub's `atrium_ci` tool and the downloaded artifacts of
runs 38784649440, 38838283227, 38890140075 and 38944460093.

## Verdict

Two causes keep it red every time. Everything else is a rotating set of flakes that adds noise on top.

## 1. The title lint (real, fails every run)

`scripts/check-titles.sh` runs last in `scripts/check-board.sh`. It fails on four lines at claude/main b33f5968:

- `js/items-data.js:131`: `out.title = wk.title`. A data property on a plain object, not a tooltip. False positive.
- `m/js/items.js:201` and `:232`: `i.title = ...`, `g.title = ...`. Real native tooltips on the phone board, added by
  633ef7a4 (item lifecycle L7, 2026-10-15). The phone board loads no `tooltips.js`, so `data-tip` shows nothing there.
  The allowlist already has this reason for `m/js/files.js`.
- `js/launchrepo.js:164`: `go.title = ...`. New in ceaf86c0 (2026-10-16). Not in the failing run, but it will fail the
  next one.

Fix: three allowlist lines in `scripts/title-allowlist.txt` (`items-data.js` and the two phone lines, each with a
reason) and a `data-tip` plus `aria-label` for `launchrepo.js`. `bash scripts/check-titles.sh` runs in under a second
and proves it.

Why it stays red: `scripts/test-touched.sh` maps changed files to board units, and this lint runs only inside the full
`check-board.sh`. A change that adds a `.title =` passes the pre-landing gate and fails after landing.

The Windows board step also failed. Its log tail shows no cause, so it is probably the same lint. The sgg card's
ANALYSIS.md or one `bash scripts/ci.sh --only board` run on Windows settles it.

## 2. Windows time-guard (environment)

The guard doubles its limits on GitHub runners (`TEST_TIME_SCALE=2`). The Windows runner is slower than that. In this
run: `api` 223.5s (limit 210s), `hubstore` 202.7s (limit 180s), and `TestStartOutsideJobAnswersTheProgramNotCmd` 11.7s
(limit 10s). The `daemon` package took 641s. Windows `go-test` takes 610 to 682s against 220 to 310s on ubuntu and
macOS. Fix: a per-OS scale for Windows, or ceilings on `scripts/test-time-allow.txt` set from Windows numbers.

## 3. Branch status test (real test bug, ubuntu and macOS every run since a3424ed4)

`x.git` in `internal/gitsync/branchstatus_integration_test.go` sets `GIT_COMMITTER_DATE` to now plus an hour, at second
resolution. The test cherry-picks `base` and `pick` onto an orphan `claude/main` and expects `claude/pick` to be landed
by `patch-id`. When the cherry-pick runs in the same second as the original commit, tree, parent, author, committer and
dates are all equal, so git makes the same SHA and the branch is an ancestor. The log shows `How:ancestry` where the
test wants `patch-id`.

Reproduced with plain git: a cherry-pick with the same committer date returns the original SHA, and a one second later
date returns a new one. On Windows each git call takes about half a second, so the second always rolls over and the
test passes (3 of 3 here, 14s each). On ubuntu and macOS git is fast, so it fails. Fix: give each `x.git` call a
strictly increasing committer date (a counter), not `time.Now()`.

## 4 to 7. Flakes

- 4: The log reads `1 messages still queued`, then `typed a held message ... could not mark it delivered: store is
  closed`. The runner typed the say after the test's 300ms wait ended. The runner is slow with 861 goroutines on a
  4 cpu Windows box. The code types first and marks delivered after, so a crash between the two would repeat the say.
  Worth a look, but not a CI cause.
- 5: `measureAfterOpen` counts the disk in a goroutine after the 201. The test reads `disk_bytes` straight away and gets
  0. It needs to wait for the measure (poll) before asserting.
- 6: The test dials 12 sockets with a 5s deadline. The macOS runner stalled two of them.
- 7: The test waits 5s for a 200ms lease to cancel. It passed 40 of 40 locally and on the other two OSes in the same
  run. Rerun in a loop on ubuntu before touching it.

## Recommendation

1. Fix the title lint (cause 1) and the branch-status test (cause 3). That alone turns ubuntu green.
2. Set the Windows time limits from Windows numbers (cause 2).
3. Add the title lint to `test-touched.sh` so a board change cannot skip it.
4. Fix the test races in 4 and 5 by waiting on the condition, not on a sleep or a first read.
5. Leave 6 and 7 alone until they repeat.
