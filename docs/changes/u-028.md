## Test plan

## @LETTER@. Images and files in the phone composer

The composer is `m/js/compose.js`, mounted on the board's phone terminal and on the /m card view. Files go up in ONE request to the card's upload endpoint, which computes its own destination. The chip row floats over the foot of the terminal on the board, so the composer keeps its 48px budget.

### @LETTER@1. Several files from the paperclip
On a phone-width board with a terminal attached, tap the paperclip and pick two photos and a PDF. Each gets a chip above the composer: a round thumbnail for a photo, a file glyph and the name for the PDF. Every path lands at the caret with the text either side kept, the composer takes focus and nothing is written to the terminal.

### @LETTER@2. The chip row
The row is one line and scrolls sideways. While the upload is going the chip says "uploading" and send is disabled. The composer is no taller than before.

### @LETTER@3. Remove a chip
Edit the text around the paths, then tap a chip's X. The chip goes and exactly its path goes from the text, and nothing else changes.

### @LETTER@4. A failed upload
Make the upload fail (stop the daemon's disk, or block the endpoint). The chip turns red and shows the reason, and no path is inserted. Its X removes it.

### @LETTER@5. Paste an image
Paste a screenshot into the composer. It uploads once, its chip appears and its path goes in at the caret. Pasting plain text, or an image with text alongside, pastes the text and uploads nothing.

### @LETTER@6. Send clears the chips
Send. The chips clear and their thumbnails are released. The same steps work on the /m card composer, through a pasted image.

## Share target, not built

Android's share sheet needs a Web Share Target in the /m manifest (`internal/api/web/m/manifest.webmanifest`, served by the hub through `internal/link/proxy.go`). Not built: the POST has to land on the hub, which is not this branch's to change.

- Manifest: `"share_target": { "action": "/m/share", "method": "POST", "enctype": "multipart/form-data", "params": { "title": "title", "text": "text", "files": [{ "name": "file", "accept": ["image/*", "*/*"] }] } }`. The manifest `scope` is `/m/`, so the action sits inside it.
- Where the POST lands: the hub, `POST /m/share`. The body is multipart, and a browser navigation cannot carry the hub's room header, so the hub must accept it with no room.
- Hub side (for @fabric): accept the multipart, hold the files under a short-lived random key in memory (size capped, expiring in minutes, never written into a card), and answer `303 See Other` to `/m/?share=<key>`. Holding the files is not an upload to a card, so the rule that files never leave a card is untouched.
- /m page side: on `?share=<key>` fetch `GET /m/share/<key>` (the files, once, then the hub forgets them), show the needs-you list as a picker ("send to which card?"), then call `mCompose.mount` for the chosen card and `mCompose.attach(files)`. Attach already does the upload, the chips and the paths, so only the picker and the fetch are new.
- Alternative needing no hub code: a service worker scoped to `/m/` that intercepts the POST, stashes the files in the Cache API and redirects. Needs a worker registered under `/m/`, and the existing `/sw.js` is at the root with its own job.
