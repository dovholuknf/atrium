# f-002: a launch key, so a retry cannot duplicate

`bug-launch-times-out-still-starts` recovers a launch whose answer was lost by a snapshot of card ids and the directory.
That narrows the window and does not close it: a retry that arrives before the late card is filed starts a second
session. A key closes it.

## Design

- The caller makes a random key on the first attempt and sends it as `launch_key` on `POST /v1/launch`. The hub's
  `atrium_launch` (`launchOnRoom`) and the stdio server's (`postLaunch`) keep it in memory per room and directory while
  an attempt's outcome is unknown, and send the same key on the next launch for that directory. An answered launch, or a
  room's refusal, lets the key go. `atrium launch` is one shot and does not retry, so it sends none.
- The room holds the key on the card: migration `0107_task_launch_key` adds `task.launch_key` and an index, not unique,
  because a key older than `store.LaunchKeyWindow` (an hour) is ignored and a new card may be filed under it. The store
  is one room's, so the key is scoped to the room.
- `Daemon.Launch` takes the key's lock, so a retry that arrives while the first attempt is still starting waits for it.
  It then looks the key up: a card found is returned with `launch_replay: true` and nothing is started. A launch onto an
  existing card (`task_id`) ignores the key.
- A launch with no key is as it was, and the snapshot recovery stays the fallback for it and for a room older than the
  field. Keys die with their card, so there is no cleanup of their own.

## Test plan

## @LETTER@. A retry after a lost answer returns the same card

### @LETTER@1. The same key

1. Launch into a directory whose runner is slow to start, and let the caller time out.
2. Launch again for the same directory.

**Expected:** the second call returns the first card with the do-not-launch-again note, and the board shows one card.

### @LETTER@2. No key

1. Post `/v1/launch` twice with no `launch_key`, for two directories.

**Expected:** two cards, as before.
