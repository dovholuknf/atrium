# f-005. What it took to make a machine contribute, and a per-project requirements file (log + design)

Status: log in progress, design not started. Owned by @fabric. Raised by clint 2026-09-29.

clint's ask: record every step taken, by us and by him, to make a machine contribute (run workers, take items, get
its branches merged here). For each: the command, what it checked, what was missing, what fixed it, which OS. Then
design `atrium.requirements`, a declarative per-project file of what a room needs to take that project's work, and
the command that checks a room against it. The design lives in `docs/room-requirements-design.md` (not written yet).

"Contribute" means all of these hold:

1. a room joined to the hub and answering on 7781
2. a runner signed in (claude, and codex where wanted)
3. the toolchain the project's workers call (git 2.39+, go, node, pwsh), on the PATH the ROOM sees
4. a clone of the repo with a fresh `hub-main`, made by push from here
5. a smoke worker that launches, reports, and exits
6. branches coming back here by `room-git.ps1 fetch <room>`

### room-git on a Windows remote wrote /cygdrive gitfiles (found by @runtime's t-005 worker on sg3)

never loaded `room-env.ps1`. So `worktree` ran Cygwin git, and every worktree's `.git` file says

`TestCullRemovesAMergedWorkersWorktreeAndBranch` is registered in it, and t-005's ref was clobbered, its real commit
79e6806 survived).

Windows. Still to do: `git worktree repair` of the four existing worktrees with Git for Windows, and `git worktree
prune` of the temp entry.

## Reboot survival, as found (for @rnd, which owns the design)

What `provision-room.ps1 -Autostart` does today:

- Windows: copies `atrium-service.ps1` and `atrium-autostart.ps1` to `~/.atrium/provision/scripts`, and installs a
  scheduled task `atrium` through `schtasks.exe` (not the CIM cmdlets, which are access denied over ssh):
  LogonType `InteractiveToken`, RunLevel `LeastPrivilege`, trigger at logon of that user. So it starts only when
  that user logs on interactively (console or RDP). An ssh logon does not fire it, and `schtasks /Run` of an
  Interactive task with nobody logged on does not bring the room up ("an Interactive task needs the user logged in
  at the machine"). No admin needed to install it. It runs through `conhost.exe --headless` so no window can be
  closed by accident, with no time limit and three restarts a minute apart. The header of
  `scripts/atrium-autostart.ps1` records why it is not S4U or "run whether logged on or not": such a task cannot
  open a pseudo terminal, and a supervised room is nothing but pseudo terminals. So on Windows today, surviving a
  reboot means the account logs on at the console (auto-logon, which needs admin to set) or a different design.
- macOS: writes `~/Library/LaunchAgents/io.github.dovholuknf.atrium.plist` and runs `launchctl bootstrap gui/<uid>`.
  The gui domain exists only while that user has a desktop login, so over ssh with nobody logged in it prints
  "not loaded now" and it loads at the next desktop login. To survive a reboot unattended, the user needs
  automatic login (System Settings, Users & Groups), which macOS hides while FileVault is on. With FileVault on, a
  reboot waits at the unlock screen until a human logs in. A LaunchDaemon would run without a login but needs sudo,
  and runs outside the user's session.
- Linux: a systemd user unit `atrium.service` with `enable --now`. `-Linger` runs `loginctl enable-linger`, which is
  the only platform where a user-level service survives logout and reboot without admin (most distros allow
  lingering for yourself).
- On every platform it first stops a room started with `--detach`, so the service does not find the ports taken.

State left today: sg3 and m1mini are detached rooms with no task, no LaunchAgent. Both die at reboot or logoff.
Standing rule: no autostart or service test against a real room. Those run on claudevm.
