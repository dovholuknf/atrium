# f-008. Hub events instead of polls: the rooms list, the inventory, and the hub's own timers (design)

Status: design, to @rnd. Owned by @fabric (hub side). The board side belongs to @ui (u-009). Raised by clint
through atrium-87300, 2026-09-29: polling is his top pain, and the rule is event driven, not polling. Ahead of the
remote gate by atrium-87300's order.

## What polls today, found in the code

The board (`internal/api/web/js`):

| Poll | Where | Every | Why it exists |
| --- | --- | --- | --- |
| `/_hub/rooms` then `/_hub/inventory` | `rooms.js` `startRooms`, `setInterval(loadHubRooms, 10000)` | 10s | a BACKSTOP. Its own comment: "the merged stream says `rooms` the moment membership changes, but a board scoped to one room is not on that stream" |
| the same two, again | every `rooms` event (`settings-spine.js`) | per event | the event carries only names, so the board fetches the lists it needs |
| `/v1/health` | `settings-spine.js` `refresh`, inside `runRefresh` every `POLL_MS` | 10s | build id (reload on a new build), `settling`, `halted` and its cause |
| `/v1/rooms` | `runners.js` `loadRooms` | when the runners pane paints | the daemon's legacy v1 room list. Not on a timer of its own |

The hub (`internal/link`):

| Timer | Where | Every | Network? |
| --- | --- | --- | --- |
| board-wide auto sweep | `autoapprove.go`, `autoSweepEvery` | 1s | YES. With the switch on, `GET /v1/permissions` on EVERY attached room, every second, whether or not anything is pending |
| stream reconcile | `events.go` `reconcile` | 1s | no. Reads `hub.Rooms()` in memory to start and stop pumps, and emits `rooms` when the names change. Runs only while a board watches |
| link heartbeat | `hub.go` `watch`, `room.go` | 5s | yes, and it stays. It is the liveness protocol, not a read of state: a room that stops beating is evicted |
| restart gate | `restartgate.go` | during a restart lease only | bounded and one-off. It stays |

So the answer to "does the hub poll rooms on a timer" is yes, once: the auto sweep, at one request per room per
second while board-wide auto is on.

Why the board's backstop exists: `feeds.emit` skips a room-scoped subscriber for any event whose `Room` is empty, and
the `rooms` event is emitted with an empty `Room`. `feeds.broadcast` already exists for exactly the other case (a hub
restart is every window's news) and is not used for `rooms`.

## The change, hub side

1. **`rooms` reaches every stream.** Emit it through `broadcast`, so a board scoped to one room hears membership
   change too. That removes the only reason for the 10s backstop.
2. **`rooms` carries the lists, so nobody fetches on it.** The payload keeps today's `rooms` (the sorted names) and
   `only`, and gains `attached` (what `/_hub/rooms` answers), `inventory` and `durable` (what `/_hub/inventory`
   answers), built by the same functions so the event and the endpoints cannot drift. It is small, one row per room.
   A board that reads only `rooms` keeps working. This bends the stream's "deltas, never state" rule on purpose, and only for this kind: the delta
   is "the rooms changed", and the new set is the cheapest honest way to say it. The re-fetch on reconnect is kept,
   so a missed `rooms` event still heals the way every other missed event does.
3. **`rooms` fires on every change the board draws, from where the change happens, not from a timer.** Today it
   fires only when the set of attached NAMES changes. It also has to fire on: a room marked or unmarked for
   deletion (`changeInventory`), forgotten (`/_hub/inventory/forget`), a join string minted or used (`Waiting`), a
   room's `cleared_at` changing, and a room reattaching with a new version. Each site calls one nudge,
   `feeds.roomsChanged()`, and reconcile emits `rooms` when a fingerprint of the full payload differs from the last
   one it sent. The nudge coalesces, so a burst of changes is one event.
4. **Reconcile wakes on a hook, not a 1s tick.** `Hub` gains one change callback, fired from attach and from
   `forget` (every eviction path goes through `forget`: hung up, missed beats, listener stopped, record gone). The
   reconcile loop waits on it, the client-arrival wake it already has, and the nudge from 3. The 1s ticker goes.
   This one is not a network poll, but clint's rule is event driven and the hook makes the ticker pointless.
5. **The auto sweep rides the permission events.** While board-wide auto is on, the approver is an internal
   subscriber for every room, so the pumps run even with no board open. A `permission` event for a pending request
   is approved on arrival. A full sweep of a room (today's `sweepRoom`) runs only at the moments deltas could have
   been missed: the switch turned on (already a nudge), a room attaching, and that room's pump reconnecting. The 1s
   ticker goes. Cost while on: one SSE per room, instead of one GET per room per second.
6. **Health without polling.** The build id changes only when the hub restarts, and a restart already drops every
   stream (with `going-down` first), so the board reads `/v1/health` once per (re)connect and no longer every 10s.
   `halted` and `settling` are the daemon's news: today nothing emits them, and the board learns them only from the
   poll. The smallest hook: the daemon emits a `health` event (`{"halted", "cause", "settling"}`) when either changes,
   and the hub relays it like any room event (tagged on the merged stream). That hook is in `internal/daemon`, so it
   is @runtime's, one call at each of the two places the fields change. A halted daemon keeps its human listener
   and its event bus up, so the event can still go out.

## The board side (u-009, @ui), named so the two halves meet

- Drop `setInterval(loadHubRooms, 10000)` and the fetches inside the `rooms` handler. Paint from the payload.
- Read `/v1/health` on connect and reconnect, and on a `health` event, not inside `refresh`.
- `/v1/rooms` (legacy) is read when the runners pane paints and on no timer. It is left alone here. If u-009 finds
  it on a timer, it is the same treatment: read on connect, and let `rooms` say when to repaint.

## Guests and what they must not see

A lent session (a guest) must never learn the room list or the inventory. The worker confirms which listener serves a
guest's stream. If any guest can reach the hub's `/v1/events*`, `broadcast` must skip guest subscribers for `rooms`,
and the same filter is where u-010's `room-stats` exclusion goes. This overlaps u-010 (item 7) enough that one
worker should do both in `events.go`: (1) the guest filter for `rooms` and `room-stats`, and (2) `os` and `arch` on
`Attached`, which then ride the `rooms` payload for free. Item 92 (`/v1/tasks/prune` reaching one room) stays
separate.

## Tests

- A room-scoped subscriber receives `rooms` when a second room attaches, and when a room is marked.
- The `rooms` payload equals what `/_hub/rooms` and `/_hub/inventory` answer at that moment.
- A burst of five inventory changes produces one or two `rooms` events, never five.
- With board-wide auto on and no board open, a pending request on a room is approved from its `permission` event,
  and no `GET /v1/permissions` is made except at turn-on, attach and pump reconnect (count requests on a fake room).
- With auto off, no pump runs when no board is open (today's rule, kept).
- Reconcile starts a pump for a newly attached room without a ticker (drive attach, assert the pump within 100ms).

## Open questions for @rnd

1. Carrying state in `rooms` (point 2) against the file's "deltas, never state" header. Recommend yes for this kind
   only, with the header saying so.
2. `last_seen` changes every beat and is not in the fingerprint, since it only draws for an offline room and is final
   at detach. Agree?
3. A CLI in another process (`atrium2 hub room token`, `room rm --force`) writes the hub's store directly. The beat
   check catches a removed record for an attached room, but a newly minted join string for a room not attached
   would not fire `rooms`. Recommend the CLI nudge the hub's loopback API after a write, best effort, rather than
   the hub watching the file.
4. The `health` event is daemon side (@runtime). Is it in this item as a one-call hook, or its own r-item?
