# u-010: the rooms menu as a live dashboard

Asked by clint, 2026-09-29: turn the "4/4 rooms" dropdown into a live dashboard, "how sexy can we make this".
Status: design, not built. Depends on @runtime's room stats event (below) for the machine and token rows.

## What it is

The chip in the header still opens the same menu, and clicking a row still focuses the board on that room
(`pickRoom`). Each row grows from one line into a small tile, and the menu becomes a panel about 560px wide,
one tile per room, with the "all rooms" tile on top as the board-wide total. Dimmed tiles for disconnected rooms
stay below, as they do today, with their `x`.

One tile, three bands:

```
 ● sg3   windows · 4h12m up · build 3b578f0  ⚠ not the hub's build ⚙
 ┌ agents ───────────────┐ ┌ tokens ───────────────┐ ┌ machine ──────────┐
 │ 7 running  2 idle     │ │ 41k/min  ▁▂▅▇▅▃▂▁▂▅   │ │ cpu 82% ▃▅▇▇▆▇▇▆  │
 │ 1 needs you  12 in 24h│ │ 24h 18.2M  cache 61M  │ │ mem 21/32 GB      │
 │ claude · codex · olla │ │ 5h 64% ███████░░░     │ │ disk 120/512 GB   │
 │                       │ │ week 31% ███░░░░░░░   │ │ 38 worktrees      │
 └───────────────────────┘ └───────────────────────┘ └───────────────────┘
```

- **agents**: running, idle, needs you (asks plus permissions, drawn in the needs-you colour and clickable to
  that room's stack filtered to waiting), done in the last 24h. The runner kinds the room has, greyed when a binary does
  not resolve.
- **tokens**: burn rate (per minute, last 5 minutes) with a 60-minute sparkline, the last 24h total, and the 5h and
  weekly limit bars. No dollars, by clint's rule.
- **machine**: CPU% with a 60-point sparkline, memory, disk free on the worktree volume, worktree count.
- **header**: OS, uptime, build, and a `not the hub's build` chip when the build ids differ, both ids in its
  hint (it says "behind" only once a build stamp carries a commit time). The transport badge moves here from the rooms tab.
- **all rooms**: sums of the agent and token numbers, the limit bars, and a count of rooms not on the hub's build.

**The limit bars are what a card last reported, not the account's state.** A 5h or weekly percentage belongs
to a vendor account, and atrium does not know which account a room or a card runs under. Two rooms can share one
account, or one room can run two. So a bar is labelled `highest seen` and carries its source in the hint: the card
that reported it, how long ago, and its reset time. Only reports from the last hour count, and a bar with none
shows a dash. The all-rooms bar is the highest across rooms under the same wording. Never summed. If atrium later
learns the account (for example from the statusline), the bars become per account and this wording goes.

Motion is small and cheap: numbers that change fade from the old value, sparklines are inline SVG polylines
redrawn from arrays, and a tile whose CPU is over 90% or that has somebody waiting gets a slow pulse on its dot.
Skins supply the colours through the existing card variables, so all 21 skins keep working.

## Where each number comes from

| Field | Exists today | Source | Owner if new |
| --- | --- | --- | --- |
| running, idle, needs you, done in 24h | yes | the board's card map (u-009) ONLY, never the event | none |
| runner kinds, binary resolves | yes, and in r-010 | harness rows today, `room-stats` runners by kind (r-010) | @runtime |
| 5h and week limit % | yes, per card | `telemetry.five_hour` and `weekly` on each card, highest reported in the last hour (see above) | none |
| build, host, since | yes | `/_hub/rooms` (`Attached.Version`, `Host`, `Since`) | none |
| hub build, not the hub's build | yes | `/_hub/health` `build`, compared to the room's `Version` | none |
| OS | sent in the room's hello, not exposed | add `os`, `arch` to `Attached` | @fabric |
| tokens per minute, today, series | partly: `/v1/usage` buckets over a window | `room-stats` event (r-010), part 2 | @runtime |
| CPU%, memory, series | no | `room-stats` event (r-010), part 5 | @runtime |
| disk, db size, worktree count | no | `room-stats` event (r-010), part 6 | @runtime |
| room process uptime | no (link `Since` is attach time) | `room-stats` event (r-010), part 3 | @runtime |

**Event driven, no polling (clint's rule).** @runtime pushes a `room-stats` snapshot on the room's
`/v1/events` every 10 seconds, sampled on its own timer, with `GET /v1/room/stats` for the first paint. The hub
already relays and tags room events, so the "all rooms" stream carries every room's snapshot and the board keeps
the latest per room. Series arrive in the snapshot (60 points), so a tab opened late still draws a full
sparkline. Nothing is fetched while the menu is open, and a closed menu costs one small event per room per 10s.
@fabric: confirm the relay passes an unknown event kind through unchanged, and expose `os` and `arch`.

**The event, as the board will read it.** This is the board's proposal for r-010. @runtime owns the final shape
and sends it back, and the preview's fixture generator and the headless mocks are written against this exact
example so the two cannot drift. A field that a wave has not shipped yet is ABSENT, not zero or null, and the band
shows a dash. Units are in the names. Times are RFC3339. Series are oldest first, one point per minute, and
`series_end` is the minute the last point covers.

```json
{
  "v": 1,
  "room": "sg3",
  "at": "2026-09-29T19:04:10Z",
  "tokens": {
    "per_min_5m": 41200,
    "hour": { "in": 812000, "out": 96000, "cache_read": 4100000, "cache_write": 220000 },
    "last_24h": { "in": 9100000, "out": 1200000, "cache_read": 61000000, "cache_write": 2900000 },
    "by_cause_24h": { "operator": 52000000, "peer": 19000000, "keepalive": 3200000 },
    "series_per_min": [38000, 40100, 44000],
    "series_end": "2026-09-29T19:04:00Z"
  },
  "process": { "cpu_pct": 3.1, "rss_bytes": 212000000, "heap_bytes": 88000000, "goroutines": 412,
               "started_at": "2026-09-29T14:52:00Z" },
  "disk": { "path": "C:/Users/claude/git", "free_bytes": 392000000000, "total_bytes": 512000000000, "db_bytes": 740000000, "worktrees": 38 },
  "runners": [ { "kind": "claude", "resolves": true }, { "kind": "codex", "resolves": true },
               { "kind": "ollama", "resolves": false } ],
  "machine": { "cpu_pct": 82, "mem_used_bytes": 21000000000, "mem_total_bytes": 32000000000,
               "cpu_series_pct": [71, 80, 82] }
}
```

`machine` and per-runner `cpu_pct` / `rss_bytes` inside `runners` are the second wave. `tokens.series_per_min`
holds 60 points in a real event and three here for brevity. The board derives the all-rooms tile itself by summing
`agents` and `tokens` across the latest snapshot per room. Nothing is precomputed on the hub.

## Stages

1. **Preview (board only).** Build the tile with the fields that exist today. For the preview, the rest come
   from a fixture `room-stats` generator enabled only by `?demo=rooms` in the URL, so clint can see the whole
   thing in `atrium preview` before any room change exists. The demo flag must never be on by default.
2. **Live.** Wire the `room-stats` event when r-010's first wave ships: agents, tokens, the room process, disk
   and runner kinds. Machine CPU and memory and per-runner CPU and memory arrive in the second wave, and their
   bands show a dash until then.
3. **Headless**: a `roomsDash` section, tiles drawn from mocked events, and no request made while the menu is
   open.

## @rnd review (accepted with changes, 7b91c72), folded

1. **One source for agent counts.** Running, idle, needs you and done come from the board's card map only.
   `agents` is gone from the event. A room-side count for rooms the board cannot see would take another name,
   and a tile never shows both.
2. **What a token counts.** `per_min_5m`, `series_per_min` and the 24h total count in + out + cache_write.
   cache_read is shown apart ("cache 61M"), because it is most of the volume and costs far less. The tile's hint
   says so.
3. **No "today".** Every day-scoped number is a rolling 24h, named `last_24h` (`by_cause_24h`), so no room's
   midnight is involved.
4. **Build.** The chip is `not the hub's build` with both ids in the hint. It says "behind" only once a build stamp
   carries a commit time.
5. **Guests.** The hub relay filters `room-stats` out of any guest (lent session) stream. @fabric states it, and
   the headless section checks it.
6. **Version.** The event carries `"v": 1`. Absent still means not shipped.
7. **For @runtime:** machine CPU and memory on Windows use GetSystemTimes and GlobalMemoryStatusEx, never CIM or
   WMI (access denied over ssh, f-005, item 75). /proc on Linux, host_statistics64 on macOS.
8. **Disk.** `disk.path` is the volume holding the room's worktree root. `worktrees` is the count of distinct
   existing card worktrees the room knows, not a filesystem or `git worktree list` scan.
9. **Phone.** phone.css: one tile per row, the bands stacked, the sparklines kept.
10. The pulse and the number fades respect `prefers-reduced-motion`.
