# r-016. A new-context cycle fails when something is typed between its steps, and the failed badge never clears (bug)

Status: diagnosed 2026-09-29, reviewed by @rnd (OK with two changes, folded), approved to build. Owned by
@runtime. Room-side.

## What happened, from the event log

**@fabric (`01a0eadc`), "the context did not clear".** The capture turn ended at 19:19:12.355. At 19:19:14.494 and
.635 the room typed two queued peer messages into the card (`pendinginject`, "typed and sent after waiting for your
line to clear"), one from the orchestrator and one from f-007. `/clear` was typed at .788, 150 ms later. It landed in
a prompt the runner was already taking, so Claude Code read it as text, not as a command, and no new session started.
u-009 reported the same thing at 18:56: "the /clear reached me as a typed message, not a command".

**@ui (`01a0eb25-b852`), "could not type the wake prompt".** `/clear` was typed at 18:55:06 and worked: the session
hook reported `source: clear` at 18:55:31.568. At 18:55:32.519 a peer message from u-009 was typed in, and ui started
a turn on it. The wake step then waited two minutes for "an empty line and no turn in progress", gave up, and filed
the cycle failed, although the context had cleared and the card was working.

## The cause, and what is already fixed

Both are the race r-007 stage 1b closes: while a card is in a cycle, every message is held until the wake prompt is
typed. 1b is on claude/main (`cd8da1e`), but it reaches the room only at the next room restart, so the room that ran
these cycles did not have it. So the root cause is fixed on main already. This item covers what 1b does not.

## The fix (reviewed by @rnd 2026-09-29: OK, with two changes, folded here)

1. **The failed chip clears only on proof the clear happened.** It clears on a SessionStart whose conversation id
   differs from the one the failed run started with (a new conversation really began), on the operator running
   new-context again (which replaces it, as today), or on the operator dismissing it. NEVER on a turn start: the
   @ui failure is the counter-example, where a peer message started a turn in a card whose context had cleared, and in
   the fabric case a turn start would wipe the chip from a card still carrying its whole old context. The reason
   stays in the card's history as an event.
2. **The wake waits out a turn, not a fixed two minutes.** After the new session has started, a turn in progress is
   waited for up to `captureEnd`, like the capture step. The cycle fails only if no gap opens.
3. **No gap between "quiet" and typing.** 1b already holds the card's peer injector and queued-message typer for
   the whole run, from the capture to the wake: `pendinginject.attempt` reschedules a held card, and `takeMessages`,
   `handleMessage` and `tellByTyping` leave messages queued. What is missing is atomicity. `ncType` does its quiet
   check (no prompt event and no turn begun for `turnSettle`, empty line, no dialog) and its write under the SAME
   input lock `injectPeer` takes, so the check and the type are one step and nothing can land between them.

No change to the steps' order, the per-card handoff name (item 91) or the hold (1b).

## Tests

- A failed cycle's chip is cleared by a later SessionStart with a new conversation id, by rerunning new-context and by
  dismissing it. A failed run followed by a peer message that starts a turn KEEPS the chip.
- The wake step with a turn in progress waits for it to end and then types the wake, instead of failing at two
  minutes. With no gap within `captureEnd`, it fails as before.
- `ncType` with a prompt event 100 ms ago waits for `turnSettle` before typing. The injector firing during
  `turnSettle` still ends with `/clear` typed first and the message after the wake.
- The fabric sequence: a queued peer message and the capture turn's end at the same moment. With 1b and the settle
  gap, `/clear` is typed alone, and a new session starts.
