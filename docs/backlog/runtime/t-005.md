# t-005. The keep-alive view re-parses every transcript on every board poll (bug)

Filed 2026-09-29 by @terminal, from a CPU profile of the live room taken during the input-lag probe. Owned by
@runtime, which owns keep-alive. Approved by the orchestrator to file, not to build.

## What was measured

The live room (pid 3704) used 72 to 122% of one core with the board mostly idle. That was measured from
`TotalProcessorTime` over three 5s samples. A 20s CPU profile from its loopback `/debug/pprof/profile` puts almost
all of its real work on one path:

```
api.(*Server).listTasks -> api.toViews -> api.toView
  -> daemon.(*keepalive).view -> readLastReply -> scanMainReplies -> scanReplies -> json.Unmarshal
```

`keepalive.view` (`internal/daemon/keepalive.go`) runs once per card on every `listTasks`. Each run opens the
card's transcript, seeks to its last `transcriptTail` (2 MB) and JSON-decodes every line to find the last reply
with usage. So every board poll decodes up to 2 MB per Claude card, for about 29 cards, and the same bytes again on
the next poll. `api.TranscriptPath` adds an `os.Lstat` per card as well.

The pty reads under `conPty.Read` show as `cgocall` in the profile. That is blocked time counted by the Windows
sampler, not CPU, and it is not this item.

It is not on the key path, because the room runs AboveNormal, but it is a core clint pays for on a machine he keeps
busy on purpose.

## The fix

Cache `readLastReply`'s answer per transcript path, keyed on the file's size and modification time. A transcript
only grows, so an unchanged size and mtime means the answer is unchanged. For a transcript that grew, a further
step (optional) is to scan only the bytes added since the cached offset and keep the last reply found, which is
what `scanReplies` already returns an offset for.

- A small map guarded by its own mutex, never by `k.mu`, so `view` stays cheap to call from the list handler.
- Evict an entry when its card is forgotten, or bound the map by count.
- `stretchState` and anything else that reads `readLastReply` should use the same cache, so the tick and the
  view agree.

## Tests

- `view` called twice on an unchanged transcript decodes it once (count calls through a seam).
- An appended reply changes the answer on the next call.
- A benchmark for `listTasks` over 30 cards with 2 MB transcripts, before and after.
- On a throwaway room only: the room's idle CPU before and after, from `TotalProcessorTime`.

## Size

Small, a few hours, in `keepalive.go` only. Needs a room restart.
