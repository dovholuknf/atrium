# r-010. A room pushes its own stats, for the rooms dashboard (feature)

Status: FIRST WAVE BUILT 2026-09-29 as r-010 (second wave, machine and per-runner cpu and rss, not built).
APPROVED 2026-09-29 by the orchestrator on @rnd's terms, all folded here, building as r-010. Filed by
@runtime at @ui's request and revised to the contract @rnd accepted with u-010 (`docs/backlog/ui/u-010.md`, "The
event" and "@rnd review"). Owned by @runtime.

## What and why

The rooms dashboard (u-010) shows each room's token burn, process, disk, runners and machine. A room serves none of
that today: only `GET /v1/health`, `GET /v1/usage` (token buckets) and loopback pprof. clint's rule is that the board
is event-driven and never polls state, so the room PUSHES a snapshot.

- **`room-stats` SSE event** on the room's `/v1/events`, every 10 seconds. The hub already retags and relays room
  events. A guest (lent session) stream never carries it (below).
- **`GET /v1/room/stats`** returns the same snapshot, for the first paint only.
- Everything is sampled on timers into one snapshot. Neither the event nor the GET does any work of its own.

## The event, version 1

ONE CONTRACT: the JSON block in u-010's "The event, as the board will read it" (`docs/backlog/ui/u-010.md`, at
`7ffc94a` on claude/ui) IS the shape. This file does not restate the fields, so the board's fixture generator, the
headless mocks and the sampler cannot drift. A change to the shape changes u-010's block first, agreed with @ui.

The rules from @rnd's review, which this build follows:

- **No `agents`.** The board counts running, idle, needs-you and done from its own card map, so the event carries
  no agent counts. A room-side count would need another name.
- **What a token counts.** `per_min_5m` (the rate over the last 5 minutes), `series_per_min` (60 points) and
  `by_cause_24h` count in + out + cache_write. `cache_read` is reported apart in `hour` and `last_24h`, because it is
  most of the volume and costs far less.
- **No "today".** Day-scoped numbers are a rolling 24 hours (`last_24h`, `by_cause_24h`), so no room's midnight is
  involved.
- **`v: 1`** on every event.
- **Absent and stale are different.** A field a wave has not shipped is ABSENT. A section whose sampler failed keeps
  its last good values and gains `stale_since: <RFC3339>`, the time of the first failed sample. Never zeros.
- **Guests never get it.** A lent session's stream (`overlay_guest.go`) is served by the room, so the room filters
  `room-stats` out of it, with a test.
- **The human listener only.** Both the event and the GET are on the board's listener, never the agent listener.
- **Disk.** `disk.path` is the volume holding the room's worktree root, with its free and total bytes. `db_bytes` is
  the database with its WAL. `worktrees` is the count of distinct existing card worktrees the room knows (from the
  store, each checked with one `os.Stat`), never a filesystem walk or `git worktree list`.
- **Machine stats never use CIM or WMI.** On Windows, `GetSystemTimes` and `GlobalMemoryStatusEx`, and for runners
  `GetProcessTimes` and `GetProcessMemoryInfo`, since CIM and WMI answer access denied over ssh (f-005, item 75).
  `/proc` on Linux. macOS through `sysctl` and `host_statistics64` via x/sys, not by execing `ps`. If anything is
  ever exec'd it is bounded (timeout, output cap) like a source.
- **Runner memory is the process tree.** claude spawns node children, so a runner's `rss_bytes` and `cpu_pct` sum its
  supervised pid and its descendants. If only the top pid is measured, the field is named `rss_top_bytes` instead.

## Waves

1. **First:** `v`, `room`, `at`, `tokens`, `process` (CPU% as a rate of process CPU time between samples, RSS, Go
   heap, goroutines, `started_at`), `disk`, `runners` (each harness row's kind and whether its binary resolves,
   reusing what the runners page already computes).
2. **Second:** `machine` (CPU% and memory, a 60-point CPU series), and `cpu_pct` / `rss_bytes` on each runner kind,
   summed over its supervised pids.

Both waves add no new dependency: the standard library, plus `golang.org/x/sys` only if it is already in `go.mod`.

## Notes for the builder

- One sampler goroutine owns the snapshot. `process` and `machine` sample every 10 s, tokens from `session_usage`
  every 10 s (one query per window), and disk on its own slower timer (minutes), which never blocks the 10 s tick.
- A room with no hub still serves both on its own address.
- Tests: the snapshot's JSON against the example above (field names and absence rules), the 10 s cadence with a fake
  clock, the GET equal to the last pushed snapshot, token arithmetic (cache_read excluded from the rate, the series
  and `by_cause_24h`), `worktrees` counting known card worktrees only, and a failing sampler that keeps its last good
  values with a `stale` mark rather than zeros.
