# r-036. The claude config lock fails instead of waiting on Windows, so a concurrent launch can fail (bug)

Status: not started. Owned by @runtime (`internal/runnersetup`, `docs/runtime/runner-setup-design.md`). Found
2026-09-30 from `TestConcurrentClaudeWritesKeepEveryChange` flaking under load in @merge's and @runtime's checks.
Room-side.

The failure: `claudetrust_test.go:307: mkdir ...\.claude.json.lock: Access is denied.`

Cause: `lockClaudeConfig` (`internal/runnersetup/claudetrust.go`) takes the lock with `os.Mkdir(path + ".lock")` and
retries only on `os.ErrExist`. On Windows, a `Mkdir` of a directory another holder has just removed and that is still
pending delete returns `ERROR_ACCESS_DENIED`, not `ERROR_ALREADY_EXISTS`. The lock then returns a hard error instead of
waiting, so the test's writer, or a real launch racing another launch's trust write, fails. Under load the window
between remove and final delete is wider, which is why it only shows then.

Fix: treat `ERROR_ACCESS_DENIED` from that `Mkdir` on Windows as contention, retried until the existing deadline, and
fail with the real error only when the deadline passes. The deadline is not raised. A deterministic test pins the
classification as a pure function (`lockBusy(err)`: `ErrExist` everywhere, access denied on Windows only). The
concurrent test then passes on the fixed code, with no timeout changed.
