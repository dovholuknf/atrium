# r-036. The claude config lock fails on Windows when launches race claude's writes (bug)

Status: BUILT on claude/r-036b. Owned by @runtime. `TestConcurrentClaudeWritesKeepEveryChange` failed about 1 in 5 on Windows.

Proven cause, by instrumenting every Mkdir, unlock Remove and stale Remove: the unlock Remove never failed (no error
in 60+ runs). The failure was the Mkdir of a waiter answering "Access is denied" (ACCESS_DENIED, not EEXIST) at the
instant a holder released the lock: the directory is delete pending while another goroutine's os.Stat of the lock
holds a handle, and lockClaudeConfig returned any non-EEXIST error at once. The follow-up os.Stat then says "cannot
find the file". So @review's guess (a dropped failed Remove leaving the lock) was not the cause.

Fix: a permission error from Mkdir is retried inside the same claudeLockWait, and reported as itself if still denied at
the deadline. The lock mechanism, claudeLockWait and claudeLockStale are unchanged; mkdirLock is a seam. Tests: a
denied Mkdir retried, and a persistent one reported. Concurrent test 20 of 20, also at -cpu 1 and beside the store tests.

The first attempt (r-036) also treated the denied answer as busy; it was backed out because the failures became 5 s
waits. I could not reproduce that shape here: with the retry, no run waited out the deadline.
