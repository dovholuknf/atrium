## r-014. report_to on launch sets a card's launcher, resolved again at each delivery

Status: BUILT on `claude/r-014`. Owned by @runtime.

A card's launcher is who `atrium_report` goes to, who hears the silent-stop notice, and who item 41's owed-report
tracking counts against. Today it is only ever the session that called `atrium_launch`. A card clint starts through gwt
(a PR review) is launched by a script, so its reports reach nobody, though @review runs that review.

- `POST /v1/launch` gains an optional `report_to`: a handle, alias or card id, resolved with the say resolver (so
  `review`, `@review` and a full handle all work). The card's launcher is set to that card, as if it had called
  `atrium_launch` itself.
- KEEP WHAT WAS NAMED, AND RESOLVE IT WHEN DELIVERING (must, from @rnd). A director's card id changes whenever it is
  relaunched, and a walk lasts hours. So the card stores `report_to` AS GIVEN (the alias or handle) next to the resolved
  launcher id. Every delivery to the launcher (`atrium_report`, the silent-stop notice, owed-report tracking) resolves
  the stored name again through the say resolver, and falls back to the stored id when the name no longer resolves. The
  launch event records both. A new column for the name goes at the END of `schema.go`'s slice.
- `atrium launch --report-to <handle>` passes it through.
- An unknown `report_to` REFUSES the launch with the list of handles that would have worked, and no card is created.
- A `report_to` naming a card on another room is refused for now: a launcher is a local card.
- It sets the launcher only. It does not change the card's tags, room or permissions.
- The human listener and the CLI only. Only the board's `/v1/launch` and `atrium launch --report-to` take it. The
  agent-side `atrium_launch` MCP tool keeps its caller as the launcher, so no agent can point another card's reports at
  a third party.
- Not counted against the launcher's limits: the launch cap and a director's worker limit do not count a `report_to`
  child against the card it reports to.
- With r-007 (idle parking, built separately): a `report_to` child IS family for r-007's wake rule and IS one of the
  launcher's own workers (it rides on the same launcher link), and does NOT get `origin:agent`.

## What was built

- Column `task.report_to` (migration `0072_task_report_to`), `LaunchRequest.ReportTo` (`report_to` on the wire) and the
  `--report-to` flag on `atrium launch`. The launch event carries `report_to` and `report_to_id`.
- `internal/daemon/reportto.go`: `resolveReportTo` (refusals), `currentLauncher` (the re-resolve, which also records
  the new card in `spawned_by` and `spawned_by_id` and moves the work item's launcher and arbiter with it), and
  `reportsToLauncher`. `launcherOf` calls `currentLauncher` first, so a report, a stop notice and a context notice all
  find the current card. The message door and `peerSaid` refresh it too, so the owed-report count follows.
- A `report_to` child gets the Stop hook and a work item, but not `origin:agent`, so the launch cap and worker count,
  which count agent-tagged sessions, never see it. A launch that carries `origin:agent` and `report_to` is refused.
