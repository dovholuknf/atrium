# r-014. `report_to` on launch sets a card's launcher, so cards clint starts through gwt report to @review (feature)

Status: approved (orchestrator), reviewed by @rnd with changes folded, building 2026-09-29. Owned by @runtime.
Room-side. From @rnd's review of the PR-start design.

## Why

A card's launcher is who `atrium_report` goes to, who hears the silent-stop notice, and who item 41's owed-report
tracking counts against. Today the launcher is only ever the session that called `atrium_launch`. A card clint
starts through gwt (a PR review) is launched by a script, not by @review, so its reports and notices reach nobody,
even though @review is the one running that review.

## The design

Reviewed by @rnd 2026-09-29: OK, with one must (keep what was named) and three statements, all folded below.

- `POST /v1/launch` gains an optional `report_to`: a handle, alias or card id, resolved with the same resolver
  `atrium_say` uses (so `review`, `@review` and a full handle all work). The card's launcher is set to that card, as
  if it had called `atrium_launch` itself.
- **Keep what was named, and resolve it when delivering (must).** A director's card id changes whenever it is
  relaunched, and a walk lasts hours. So the card stores `report_to` AS GIVEN (the alias or handle) next to the
  resolved launcher id. Every delivery to the launcher (`atrium_report`, the silent-stop notice, owed-report tracking)
  resolves the stored name again through the say resolver, and falls back to the stored id when the name no longer
  resolves. The launch event records both. A new column for the name goes at the END of `schema.go`'s slice,
  tolerant of already existing.
- `atrium launch --report-to <handle>` passes it through.
- An unknown `report_to` REFUSES the launch with the list of handles that would have worked (the say path's refusal),
  rather than launching a card that reports to nobody.
- A `report_to` naming a card on another room is refused for now: a launcher is a local card.
- It sets the launcher only. It does not change the card's tags, room or permissions.
- **The human listener and the CLI only.** Only the board's `/v1/launch` and `atrium launch --report-to` take it.
  The agent-side `atrium_launch` MCP tool keeps its caller as the launcher, so no agent can point another card's
  reports at a third party. Adding it to the MCP tool would be a separate decision.
- **Not counted against the launcher's limits.** The launch cap and a director's worker limit do not count a
  `report_to` child against the card it reports to: a script or clint launched it, not that director. (@review's
  PR-start design assumes its limit of 2 ignores gwt cards.)
- **With r-007 (idle parking), stated for its stage 5 worker:**
  - A `report_to` child IS family for r-007's wake rule, so its report or say wakes a parked launcher.
  - It IS one of the launcher's own workers for the park rule, so the launcher does not idle-park while it is live.
  - It does NOT get `origin:agent`, so the child stays clint's own card and is exempt from idle parking unless it is
    tagged `atrium:park-idle`.

## Tests

- A launch with `report_to: review` makes the card's launcher @review's card: `atrium_report` from it reaches @review,
  and a silent stop notifies @review.
- An unknown `report_to` is refused, with the list, and no card is created.
- The CLI flag reaches the endpoint. The MCP `atrium_launch` has no such field and keeps its caller.
- Owed-report tracking (item 41) counts the card against @review.
- Relaunch the target under the same alias (a new card id), then `atrium_report` from the child reaches the NEW card.
  With the name gone entirely, it falls back to the stored id.
- A `report_to` child does not count against its launcher's launch cap or worker limit.
