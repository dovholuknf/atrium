# r-034. Standing rules that name MCP tools

Status: BUILT 2026-09-30 on `claude/r-034` by @runtime's worker, to the design accepted by @rnd. Room-side: live at the
next room restart. The board part is @ui's, see below.

Design: `docs/runtime/mcp-rules-design.md`. Code: `internal/mcprule` (what a name may be), `internal/store/rules.go`
(`AddMCPRule`, the wider candidate query, tie to block), `internal/claudeconf/claudeconf.go` (`convertMCP`,
`dropShadowedMCP`), `internal/api/api.go` (add, import and approve-forever routes), `internal/daemon/daemon.go` (the
decider recorded for an MCP rule). Tests: `internal/store/rules_mcp_test.go`, `internal/claudeconf/claudeconf_mcp_test.go`,
`internal/api/mcprules_test.go`, `internal/daemon/mcprule_test.go`.

Decided with @rnd:

- A tie between matching rules goes to block, for every rule.
- Deny-first at import for Bash, Edit and the rest is NOT done. To be filed separately.
- cr48 cli finding 01 stays separate.
- An MCP `ask` entry shadows an allow like a deny. The allow is dropped and reported.

For @ui:

- `Rule.note` is new on the rules list. It reads `matches this exact input only` for an old MCP rule that carries a
  real prefix, so the list can say why it never fires. The wording is the board's.
- The decider recorded for an MCP rule is its tool pattern, so `gotoRule` in `stack.js`, which finds a row by its
  displayed prefix, cannot find one. It should match on `r.tool` for an MCP rule. Until then the link toasts "no rule
  matches".
- The "always" and "never" buttons on an `mcp__` card should say "this tool", with a way to cover the server (a second
  `POST /v1/rules` with `mcp__s__*`). The import dialog needs wording for the new skip reasons.

Not done: the design's `include_broad` wording on the dialog (board), and anything for cr48 finding 01.
