# t-003. A second viewer of another height does not resize the pty (design)

Raised 2026-09-29 by @terminal, approved for design only by the orchestrator. Owned by @terminal. It covers what
is left of item 74 and t-002 step 3 without OpenConsole.

## The problem

The pty has one size and a card can have several viewers. `agreedViewport` (`internal/daemon/supervisor.go`) gives
it the WIDEST viewer's width and the SHORTEST viewer's height. Width was settled already: a narrower viewer
scrolls sideways (`markWide`) and nobody else pays. Height was not. A phone, a shorter pop-out or a shorter pane
attaching makes the pty shorter, and its leaving makes it taller again.

Each row change on the inbox ConPTY ends in a bare `ESC [ H` repaint that is shifted against what was on the
screen. When the new row 1 is later than the old one, rows are overwritten and never reach history (item 74's
loss). When it is earlier, rows already in history are filed a second time (t-002's duplicates). The height hold
(`387ccd5`) stopped fast flips from being coalesced. It does not stop a real change, and every attach and detach
of a shorter viewer is one. A phone's on-screen keyboard is two more.

## The design

**Rows follow the TALLEST viewer, the same way columns follow the widest.** A shorter viewer draws the pty's full
height in a box clipped to its pane, the vertical twin of `markWide`. So the pty moves only when the tallest viewer
changes, and a phone, a short pop-out or a keyboard opening moves nothing.

This is order independent for the same reason widest is (the comment above `viewport` says why that matters). The
tallest viewer is almost always clint's main pane, so in the common case the pty never changes height after the
first attach.

**A shrink waits longer than a grow.** Once the tallest viewer leaves, the agreed height falls to the next one.
Nothing is wrong while it waits, because the viewers left can all clip. So a shrink holds for `shrinkHold` (5s),
and a grow keeps `heightHold` (500ms). A reload of the main pane, which drops its socket and comes back, is then
never a resize, even on a slow reload. A viewer on its own that flips its height inside 5s (a phone keyboard) is
none either.

**The first viewer still sets both at once** (t-002 step 2, unchanged). The last viewer leaving still keeps the
size it had (unchanged).

### Daemon (`supervisor.go`)

- `agreedViewport`: `rows` is the max rather than the min. Rewrite the "ROWS STILL FOLLOW THE SHORTEST" paragraph,
  because its reason (a taller pty puts the prompt below the pane's edge) is what the board half answers.
- `holdHeight` takes `shrinkHold` when `want < applied` and `heightHold` otherwise. `r.hold` stays the override
  for tests and scales both.
- Nothing else. The `{"t":"size"}` frame already carries rows, and `applyHeld` already re-reads the viewers.

### Board (`js/terminal-links.js`, `css`)

- `ptyRowsFor(fit)` returns `termPtyRows` when the daemon has said one, so xterm always draws the pty's height,
  shorter or taller than the pane. A taller pane keeps today's behaviour (the grid sits on the footer).
- A pane shorter than the grid gets class `tall` on `#t-screen`. The `.xterm` element is sized to the grid's pixel
  height, and `#t-screen` clips it with `overflow-y: hidden`. There is no second scrollbar, because xterm's own
  scrollbar stays the only vertical one. The fit addon measures `#t-screen`, so the fit still proposes what the pane
  can show and this is not a feedback loop, the same as `markWide`.
- **The clip follows the cursor.** On every render, `#t-screen.scrollTop` is set so the cursor's row is visible
  with one row below it where there is one. Claude Code's prompt is where the cursor is, so typing is always in
  view. A fresh session with its prompt near the top shows the top, and a full screen shows the bottom.
- Nothing becomes unreachable. Scrolling xterm up by k lines moves every row down k, so the rows the clip hides
  come into view. Only the first few lines of the whole buffer need the pane to be taller.
- Mouse, selection and the link provider read xterm's own element rectangle, which moves with the clip, as they
  already do with the sideways scroll. The headless test pins this.
- The popped-out window takes the same path (`applyPtySize` and `fitTerm` are shared).

### The order it ships in

**The board half first, alone.** It is HUB-SIDE and safe on an old room: an old room never makes the pty taller
than any viewer, so `tall` never switches on.

**The daemon half second, with a room restart.** It must not land ahead of the board. An old board would draw
`min(fit, pty)` rows against a taller pty, and every absolute row would be off (the bug described above
`termPtyRows` in `terminal.js`). The board reloads itself on a build id, so one board deploy before the room
restart is enough.

## Rejected

- **The oldest viewer owns the height.** It moves even less, but it depends on order. The main pane reloading
  makes a phone the oldest, and the phone then shrinks everyone. That is the order dependence the width rule was
  written to avoid.
- **A lone viewer never shrinks the pty.** A phone opened on its own would then draw a 50-row pty in a 20-row box
  for good. `shrinkHold` gets most of the benefit without that.
- **Letting xterm's viewport scroll the clipped rows** (`#t-screen` with `overflow-y: auto`). That puts two
  vertical scrollbars on one pane, and the wheel scrolls whichever is under the pointer.

## What clint would notice

Opening a card on the phone, in a shorter pop-out or in a split pane no longer loses lines or doubles the banner in
the main pane. On the phone the top few rows of the live screen are clipped until you scroll up a little, which is
the height version of the sideways scroll narrow windows already have.

## Tests

Go, fake pty, in `internal/daemon` (`-run 'Viewport|Hold|Tallest'`):

- A shorter second viewer attaching calls `Resize` zero times, and the size frame it gets carries the taller rows.
- The tallest viewer leaving calls `Resize` zero times within `shrinkHold`, and once after it.
- The tallest leaving and coming back inside `shrinkHold` (a reload) calls `Resize` zero times.
- A lone viewer's rows going 40, 25 and back to 40 inside `shrinkHold` calls `Resize` zero times.
- A taller viewer arriving grows the pty after `heightHold`, as today.
- The first viewer still resizes once, with both sizes.
- `-race` over the same run (item 53's locking must still hold).

Headless (`HEADLESS_ONLY=tallClip`):

- A pane whose fit is 20 rows gets a size frame of 48: `term.rows` is 48, `#t-screen` has `tall`, and the cursor's
  row is inside `#t-screen`'s rectangle, with the cursor at row 3 and again at row 47.
- A wheel up of 5 lines shows the rows the clip hid.
- The next fit still proposes 20 rows, so there is no loop.
- A click on a file link inside the clipped grid opens that link, which pins the coordinates.
- A size frame of 20 takes `tall` off.

Capture, on a throwaway room only, with the `conpty_scroll_repro_test.go` harness through a runner
(`ATRIUM_CONPTY_VIA=runner`): a 300-line reply streamed while a second viewer 10 rows shorter attaches and detaches
three times. Before the change it loses lines, and after it `/scrollback/text` holds all 300. On the live room, the
74b loss report (`?repair=report`) should show fewer shifted repaints once this is deployed, which also feeds
item 74's option 2 or 3 decision.

## Size

One worker, about a day: about 15 lines and a rewritten comment in `supervisor.go`, about 40 lines of board JS and
a CSS rule, and the tests. Two deploys: the board half (hub-side), then the daemon half (room restart).

## Open question for clint

Is a clipped top on the shorter viewer acceptable? The alternative that loses nothing is OpenConsole (item 74
option 2), which costs two or three workers and packaging.

## Alternative: a phone view and a desktop view that never disturb each other

clint's answer, 2026-09-29, was a question: can there be two views, one for the phone and one for the desktop,
where neither disturbs the other? One pty has one size and Claude Code draws for that size, so the phone cannot be
a second live terminal at its own size. What it can be is a viewer that never takes part in the size.

**That part costs nothing on the daemon.** A viewer goes into `r.views`, and so into `agreedViewport`, only when
it sends `{"t":"resize"}` (`setViewport` in `supervisor.go`). An attach that never sends one waits `sizeWait`
(60ms) and gets the backlog at whatever size the pty is already. So "the phone never disturbs the desktop" is one
board rule: on a phone, never send a resize. The pty stays at the desktop's size while the phone watches, and it
keeps the size it had when the phone is the only viewer, the way it does now when the last viewer leaves.

**What every option still needs on the phone: a key bar.** Claude Code's own menus (a question with choices, plan
approval, `/resume`, interrupting with Esc) need Esc, the arrows, Tab and Enter, and a phone keyboard has no Esc
key. The board has a help line under the terminal, not keys. Atrium's own permission requests are separate: they
are rows on the board (`.row.perm`), already laid out for a phone, and they work the same under every option here.

### (a) The phone view is not a terminal

It is text: the reply as the transcript says it (`sessionexport.go` already turns the JSONL into Markdown) or the
reflowed scrollback from `screen.go` (`/scrollback/text`). Under it go the live bottom rows of the screen and an
input box, which sends `{"t":"in"}` frames on an attach that never resizes.

- **On the phone:** prose that wraps at the phone's width, readable without zoom or panning. It shows no colour
  and no live redraw, a spinner reads as a line of text, and a menu's highlighted choice is lost unless the
  bottom rows are drawn with their colour.
- **Typing and approvals:** typing works through the box. Claude Code's menus work through the key bar, but you
  choose from a text picture of the menu, which will be wrong at times. Atrium's approvals work.
- **Cost:** the most. A new view, a tail endpoint for the live rows (or `/scrollback/text` polled), Markdown on
  the board, and the key bar. Two or three workers, all board side except the tail endpoint. The transcript also
  only has a reply once Claude Code writes the line, so a long reply appears in pieces.

### (b) The phone view is the desktop's terminal, scaled or pannable

xterm on the phone is set to exactly the pty's columns and rows from the `{"t":"size"}` frame and never sends a
resize. It opens scaled to the phone's width, with pinch zoom and panning.

- **On the phone:** the same screen the desktop sees, colour and redraw included. At the default 120 column floor,
  a readable 11px font shows about 60 columns in portrait and about 125 in landscape. So a reply is read by panning
  sideways in portrait, or read comfortably in landscape. Scaled to fit it is a thumbnail you can take in at a
  glance but cannot read.
- **Typing and approvals:** everything works, because it is the real terminal. Menus work through the key bar.
  Atrium's approvals work.
- **Cost:** the least. Board only and hub side. One deploy and no room restart. About a day for one worker: in
  `fitTerm`, a phone sets xterm to the pty's size and never sends a resize. Add a CSS transform with pan and
  zoom, the key bar, and a headless test that a phone attach sends zero resize frames. The Go test is that an
  attach with no resize frame leaves `r.views` empty and calls `Resize` zero times.
- **It removes the phone as a cause of item 74's loss at once**, before any daemon change, because the phone
  never moves the pty.

### (c) t-003 as designed above: rows follow the tallest viewer, the shorter one clipped

- **On the phone:** the terminal at the phone's font, with the top rows clipped and the clip following the cursor.
  It scrolls sideways where the pty is wider, the same as (b) in portrait without zoom.
- **Typing and approvals:** all of it works, the same as (b). The phone needs the key bar here too.
- **Cost:** one worker for about a day, and two deploys: the board, then the daemon with a room restart. It is the
  only option that also covers a shorter pop-out or split pane on the desktop, which (a) and (b) leave as they are.
- **The phone alone still resizes the pty**, because it is the tallest viewer when nobody else is attached. With
  (b) it never does.

### Recommendation

**(b) first.** It is the smallest and ships hub side with no room restart. It is the only one that gives clint
the exact rule he asked for, that the phone never moves the pty. Every input works because it is the real
terminal. Then decide on the rest from use:

- If reading replies by panning is the complaint, (a) is a reading tab added beside (b), not a replacement, and it
  reuses the same no-resize attach and key bar.
- If shorter pop-outs and split panes on the desktop keep causing losses, the daemon half of (c) is still the
  answer there. Its board half is mostly written by (b) already, because xterm drawing the pty's size in a smaller
  box is the same code.

### Decision and review

clint picked (b), 2026-09-29, and it is being built as t-003b. @rnd reviewed (b) after that and accepted it with
these changes, which are part of t-003b:

1. **Not one resize frame from a phone**, not even one equal to the pty's size. Any sender enters `r.views` and
   votes on the height for as long as it is attached. Both board send sites are gated: `sendResize` on attach and
   `sendResizeSettled` after a fit. Tested with a size frame arriving while the phone is attached, the keyboard
   opening, and a rotation.
2. **Zoom is `fontSize`, never a CSS transform.** A transform puts clicks, selection, links and mouse reports on
   the wrong cell. Pan is a native overflow scroll around a grid of the pty's size. Portrait opens at about 60
   columns and landscape at the full width.
3. **The pan follows the cursor** on every render and on a `visualViewport` resize, so the on-screen keyboard never
   covers the prompt. Option (c) reuses this for its clip.
4. **A phone is `(pointer: coarse)` plus a narrow width**, never the user agent. It can be overridden either way per
   terminal. "Fit this screen" joins the size vote, so it is greyed out with a warning while another viewer is
   attached.

The key bar is Esc, Tab, Shift+Tab, the arrows, Enter and Ctrl+C, and Ctrl+C takes a long press or a confirm.
**A phone that is the first viewer after a restart leaves the pty at its launch size** until a desktop attaches.
That is intended. Do not "fix" it by letting the phone set the first size.

(a) and (c) are filed, not approved, and not yet reviewed by @rnd.
