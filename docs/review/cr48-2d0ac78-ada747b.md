## HIGH: a directory-named report can halt the store (r-036)

`Register` with `NameSource == dir` (tasks.go:186-195) looks the name up only among cards that are not done and not
archived, so a finished card holding that name is invisible. When nothing matches, the pid plus worktree fallback
(198-205) can pick a different, live card, and `refreshObserved` (300-303) writes the done card's name onto it.
`UNIQUE (wire_name)` (schema.go:38) refuses. That error is not transient (store.go:736), so `guard` halts the store
(store.go:778-780) and every later call answers ErrHalted until a restart. The stale-name check at 206-218 runs only
when the pid fallback also missed.

Exposure: an unbound hook (no `ATRIUM_TASK_ID`, meaning a joined or external session or an older hook) whose
directory base name (`hookAgent`, cli/join.go:91) equals a done card's name, in a checkout where a live card has the
same pid and worktree under another name. Two cards in one checkout is the case r-021b was written for. The result is
the worst outcome the daemon has: a hook, which must never fail a session, stopping the whole room. Introduced by
da682110 (r-021b). Proven: `TestScratchDirNameOnPidMatchCollidesAndHalts` prints
`store is halted: constraint failed: UNIQUE constraint failed: task.wire_name (2067)`. The store slice found no
second path.

## MEDIUM: a nested claude is taken for its parent (r-037)

A `claude -p` started from a session's Bash tool inherits `ATRIUM_TASK_ID` and `ATRIUM_AGENT_NAME`, so its hooks
name the parent card. r-021 closed this for SessionStart with `ownsSession`. Three other doors are still open, and
all three have the same cause.

- **Session end and compact** (session.go:171-176, 242-253). `ownsSession` is asked only for starts. The resume claim
  and `Observe` run for every event. A nested end replaces the parent's resume id with the nested conversation's,
  writes the nested pid, and `case "end"` sets the parent done or dead and drops its queued messages.
  `TestScratchNestedEndMovesResumeAndEndsParent` shows `resume="nested-9" status=dead pid=200`. The existing test
  `TestANestedClaudeCannotChangeTheParentsResumeID` covers start and Stop only.
- **Stop** (messages.go:231-317). The resume id is refused, but the handler goes on. `refreshObserved` sees a
  different resume id and writes pid 0 (proven: `pid before=100 after=0`). From reading, not run: `turnEnded` marks
  the parent needs-input while it works, a silent-stop notice can reach its launcher, and `takeMessages` can hand a
  message queued for the parent to the nested session's Stop hook, which throws it away.
- **Permission** (cli/hook_permission.go:102, daemon.go:708-716, tasks.go:293-303). The request carries the parent's
  name and the nested pid, and `Register` writes it. `TestScratchNestedPermissionOverwritesParentPID` shows 100
  become 200. On an unsupervised card the reaper (reaper.go:150) then asks the OS about the nested pid, so the parent
  can be filed dead when the nested run exits (from reading). This is live today: the installed
  `atrium-perm-hook.ps1` sends the same name and the same nearest-claude pid (lines 122-137, 191).

The cli half is one missing field: the Stop and activity hooks send no pid (turn.go:224, hook.go:413), and the
permission hook sends no task id, so the daemon has nothing to run `ownsSession` against.

## MEDIUM: notify's question and finished reasons never fire (f-020)

`NotifyIdentity` (link/notify.go:154-191) reads `questions_at`, `open_questions`, `turn_ended_at` and `unseen` at the
top level of the card payload. Rooms announce `/v1/state`, which is the raw `store.Task` rows (api/state.go:42-58,
kept whole by link/announce.go:279-316). Those four keys live only in `store.SeenView` (store/seen.go:83-98), which
`/v1/state` does not include. So a question notifies as `input`, a finished turn as `input`, and `finished` never
fires. The unit tests hand-build flat payloads no room sends. `TestCR48RoomPayloadNeverCarriesQuestionOrFinished`
passes on a real `store.Task`. Introduced by 83aaae28 (f-017). Owner fabric, with the api payload shape.

## MEDIUM, as a question: can a remote caller set the program the hub runs? (f-021)

`PUT /_hub/notify` stores an argv the hub executes and `POST /_hub/notify/test` runs it at once. `serveHubAPI` routes
both with no caller check (proxy.go:1278-1279), while `serveControl` (1218) and `serveNudge` (1243) refuse anything
but `loopbackRemote`. The scratch test got 200 on both from 203.0.113.7. `/test` is a bare POST, so it is also a
simple cross-origin request, and repeated calls start concurrent processes. What is not proven is whether any real
deployment puts an untrusted caller on the hub's board listener. Should PUT and `/test` take the same loopback gate
as `/_hub/mcp`? Or is a board share meant to be trusted with running a command on the hub host, and if so, where is
that written down?

## Refuted

cli 01 said `permSkipTools` (hook_permission.go:33) lets `mcp__*` tools through to `/permission` where
`atrium-perm-hook.ps1` skipped them. The script skips neither. Its list is the same eight names
(dotfiles `claude/hooks/atrium-perm-hook.ps1`, the installed copy under `~/.claude/hooks`, matcher `""`), and neither
file mentions `mcp__`. The Go hook does what the script does. Whether MCP tools should be gated at all is r-034's
question (standing rules that name MCP tools), not a regression.

## Checked and fine

- Hook posture: `hook`, `session` and `turn` return exit 0 on any error (cli.go:73-77). The permission hook prints
  nothing on every failure path, fails open on `/gate` down, slow or undecodable, and bounds stdin and response
  bodies. `/activity` is one second, one attempt, no retry.
- `/gate` qualifies the name inside `GatedByWireName` (store/tasks.go:1354), so a machine name prefix does not
  mismatch.
- `ErrStaleName` is returned after `guard` with a nil error, so it cannot halt. `Register` with a told name behaves as
  before.
- Migrations: store/schema.go changed only comments. hubstore `0003_notify_sent` is appended at the end, is `IF NOT
  EXISTS`, and changes no UNIQUE constraint.
- The notify worker: no shell, argv as given, `WaitDelay` set, output capped while read, one goroutine, drop-oldest
  queue, no lock held across `Send` or the store. `Announced` runs after the announcement is stored and never delays
  it.
- Replies: `keepHead`/`keepTail` never split a rune, the cache is mutex-guarded, copied out and bounded at 400.
- Ancestry: `runnerNames` and `maxHops` are shared, and every platform walk is bounded, so a parent cycle cannot spin.
- About 150 of the changed files are doc-path comment edits with no behaviour change, checked by filtering each diff
  for non-comment lines.
